# Шпаргалка к защите КР1 — «Киберспортивный клуб»

Ответы на вопросы из задания со ссылками на код. Пути указаны относительно
`src/main/java/ru/mirea/cyberclub/`.

## Назначение основных классов

| Класс | Слой | Назначение |
|---|---|---|
| `Main` | — | точка входа: настройка кодировки и ANSI-цветов консоли, загрузка `db.properties`, проверка соединения с БД, запуск `ConsoleApp`; при недоступной БД печатает подсказку и завершает работу с кодом 1 |
| `ui/ConsoleApp` | UI | «сборка» приложения: создаёт репозитории, сервисы, экспортёры и меню, связывая их через конструкторы (ручное внедрение зависимостей) |
| `ui/AbstractMenu` и наследники (`MainMenu`, `ClientMenu`, `StationMenu`, `BookingMenu`, `SearchMenu`, `FilterMenu`, `SortMenu`, `ExportMenu`, `DbTablesMenu`, `ThemeMenu`) | UI | цикл «показать пункты → прочитать выбор → выполнить → вернуться в меню» и единая обработка ошибок |
| `ui/ConsoleIO` | UI | безопасный ввод (числа, даты, суммы, enum) и вывод с учётом темы |
| `ui/TablePrinter` | UI | печать списков сущностей выровненными таблицами |
| `service/ClientService`, `StationService`, `BookingService` | Service | бизнес-правила и валидация; сервисы не знают про SQL и про консоль |
| `service/StatisticsService` | Service | сбор показателей и формирование строк отчёта (общих для консоли и экспорта) |
| `repository/*` (интерфейсы) | Repository | контракты доступа к данным: `CrudRepository<T,ID>` + специализированные методы поиска/фильтрации |
| `repository/jdbc/*` | Repository | реализация через JDBC; `AbstractJdbcRepository` — общий шаблон запроса, `SqlErrorTranslator` — перевод `SQLException` в исключения приложения |
| `model/*` | Model | сущности `Client`, `Station`, `Booking` (наследуют `BaseEntity`), перечисления `StationType`, `BookingStatus`, record `Statistics` |
| `export/*` | Export | интерфейс `Exporter` и реализации `ExcelExporter` (Apache POI), `CsvExporter` |
| `util/DatabaseManager` | Util | выдаёт `Connection` по параметрам из `AppConfig`, проверяет доступность БД |

## Инкапсуляция

Все поля сущностей `private`, доступ только через геттеры/сеттеры (`model/Client.java`,
`model/Booking.java`). Идентификатор инкапсулирован в `BaseEntity`. Внутренние проверки
сервисов — `private` методы (`BookingService.checkOverlap`, `validateInterval`), снаружи
доступны только операции предметной области (`create`, `changeStatus`, ...). Параметры
подключения скрыты в `AppConfig`/`DatabaseManager`. Состояние `AbstractMenu` (список пунктов)
`private`, наследники добавляют пункты через `protected add(...)`.

## Интерфейсы

* `repository/CrudRepository<T, ID>` — обобщённый контракт CRUD; `ClientRepository`,
  `StationRepository`, `BookingRepository` расширяют его. Сервисы зависят только от интерфейсов,
  поэтому в тестах JDBC-реализации заменены на in-memory (`src/test/java/.../repository/InMemory*`),
  а в КР3 их можно заменить на Spring Data без изменения сервисов.
* `repository/StatisticsRepository`, `repository/SchemaInspector` — отдельные контракты для статистики
  и просмотра схемы.
* `export/Exporter` — единый контракт экспорта; `ExportMenu` строит пункты по списку `List<Exporter>`
  и не знает, какой формат за каким пунктом.
* Функциональные интерфейсы `ParameterSetter` и `RowMapper<T>` в `AbstractJdbcRepository` —
  передача кода заполнения параметров и разбора строки лямбдами.

## Применение enum

* `model/BookingStatus` — статусы брони **со схемой переходов внутри enum**
  (`allowedTransitions()`, `canTransitionTo()`, `isFinal()`, `isEditable()`): бизнес-правило
  «запрещённый переход» описано рядом с данными, а `BookingService.changeStatus` только вызывает проверку.
* `model/StationType` — типы мест с названием для отображения и признаком `isAdultsOnly()`.
* `service/BookingSortField` — поля сортировки, каждый элемент хранит свой `Comparator<Booking>`.
* `ui/ConsoleTheme` — темы консоли с ANSI-кодами цветов.

В БД значения enum хранятся строкой с ограничением `CHECK (status IN (...))`; преобразование —
`BookingStatus.valueOf(rs.getString("status"))` и `status.name()` при записи.

## Полиморфизм

* `BaseEntity.describe()` — абстрактный метод, у `Client`, `Station`, `Booking` своя реализация;
  меню вызывает `entity.describe()`, не зная конкретного типа.
* `AbstractMenu.run()` — общий алгоритм, а `printTitle()` и `exitLabel()` переопределены в `MainMenu`
  (баннер и «Выход» вместо «Назад»).
* `Exporter` — `ExportMenu.export(Exporter)` вызывает `exporter.export(data, dir)`, реально
  выполняется `ExcelExporter` или `CsvExporter`.
* `CrudRepository` — сервис работает с `BookingRepository`, за которым стоит `JdbcBookingRepository`
  (в приложении) или `InMemoryBookingRepository` (в тестах).
* Перегрузка конструкторов у сущностей и сервисов (с `Clock` и без).

## Использование коллекций

* `List<Booking>` — результаты всех выборок; `ArrayList` внутри `AbstractJdbcRepository.queryList`.
* `Map<String, String>` (`Map.ofEntries`) — сообщения для ограничений БД в `SqlErrorTranslator`.
* `EnumSet<BookingStatus>` — допустимые переходы статусов; `EnumMap<BookingStatus, Long>` — число броней
  по статусам в статистике.
* `Optional<T>` — результат `findById`/`findByNickname`.
* Stream API: сортировка `BookingService.sorted` (`stream().sorted(comparator).toList()`),
  фильтр по стоимости `filterByPriceRange`, предстоящие брони `getUpcoming`, `Collectors.joining`
  для списка допустимых статусов, `Comparator.comparing(...).reversed().thenComparing(...)`.

## Обработка исключений

Иерархия собственных исключений (`exception/`): `AppException` (unchecked) →
`EntityNotFoundException`, `ValidationException`, `BusinessRuleException`, `DataAccessException`,
`ExportException`, `InputCancelledException`.

* Слой Repository: `SQLException` перехватывается в `AbstractJdbcRepository` и переводится в
  `DataAccessException` / `ValidationException` / `BusinessRuleException` по SQLSTATE
  (`SqlErrorTranslator`: 23505 — уникальность, 23503 — внешний ключ, 23514 — CHECK, 23P01 — EXCLUDE, 08xxx — соединение).
* Слой Service: бросает `EntityNotFoundException` (нет записи), `ValidationException` (некорректные данные),
  `BusinessRuleException` (нарушение правила).
* Слой UI: `AbstractMenu.execute` ловит их и печатает `Ошибка: ...`; `ConsoleIO.readLong/readDate/...`
  ловят `NumberFormatException`/`DateTimeParseException` и повторяют запрос; общий `catch (RuntimeException)`
  не даёт программе упасть; `Main` ловит `DataAccessException` при старте (нет подключения к БД).
* `try-with-resources` закрывает `Connection`, `PreparedStatement`, `ResultSet`, `Workbook`, `Writer`.

## Работа JDBC

`util/DatabaseManager.getConnection()` → `DriverManager.getConnection(url, user, password)`
(драйвер `org.postgresql.Driver` подключён через Maven). Каждый метод репозитория:

```java
try (Connection connection = db.getConnection();
     PreparedStatement statement = connection.prepareStatement(sql)) {
    params.set(statement);                       // statement.setLong(1, id) ...
    try (ResultSet rs = statement.executeQuery()) {
        while (rs.next()) result.add(mapper.map(rs));   // rs.getString("nickname") ...
    }
} catch (SQLException e) {
    throw SqlErrorTranslator.translate(e, "выборка данных");
}
```

(`repository/jdbc/AbstractJdbcRepository.queryList`). Вставка получает сгенерированный ключ через
`Statement.RETURN_GENERATED_KEYS` + `getGeneratedKeys()`. Даты передаются как `Timestamp`/`Date`,
деньги — `BigDecimal` (`setBigDecimal`/`getBigDecimal`). Структура БД читается через
`DatabaseMetaData.getTables/getColumns` (`JdbcSchemaInspector`).

## Statement vs PreparedStatement

`Statement` выполняет готовую строку SQL: параметры приходится склеивать (`"... WHERE email = '" + email + "'"`),
что открывает SQL-инъекцию (`' OR '1'='1`) и ломается на кавычках в данных. `PreparedStatement`
компилируется с плейсхолдерами `?`, значения передаются отдельно (`setString`, `setLong`, ...) и
экранируются драйвером; запрос можно выполнять многократно с разными параметрами, типы проверяются.
В проекте используется только `PreparedStatement`; единственное место с конкатенацией — имя таблицы
в `JdbcSchemaInspector`, где оно берётся из списка, полученного от самой БД, и заключается в кавычки.

## Связи между таблицами

`bookings.client_id → clients.id` и `bookings.station_id → stations.id` — связи «один ко многим»
(один клиент — много броней, одно место — много броней), объявлены как `FOREIGN KEY ... ON DELETE RESTRICT`:
удалить клиента/место с бронями нельзя. При выборке броней выполняется `JOIN` с обеими таблицами,
чтобы показать ник клиента и название места (`JdbcBookingRepository.SELECT`).
Прочие ограничения: PRIMARY KEY (`BIGSERIAL`), UNIQUE (ник, телефон, email, название места),
NOT NULL, CHECK (форматы, допустимые значения enum, `end_time > start_time`, `hourly_rate > 0`),
EXCLUDE (пересечение броней). См. `db/01_schema.sql` и `docs/er-diagram.md`.

## Основные бизнес-правила

См. таблицу в README (10 правил). Ключевые: существование клиента/места (1), место не на обслуживании (2),
корректный интервал 30 мин – 12 ч и не в прошлом (3), отсутствие пересечений (4), схема переходов
статусов (5), ограничения на изменение/удаление по статусу (6), возраст 18+ для VIP/буткемпа и ночи (7),
валидация и уникальность клиента, запрет удаления с незавершёнными бронями (8), автоматический расчёт
стоимости (9), запрет удаления места с историей (10). Все — в `service/`, покрыты тестами
`src/test/java/.../service/*Test.java`.

## Поиск, фильтрация и сортировка

* Поиск (меню 4): по нику клиента, названию места, комментарию — SQL `ILIKE ?` с экранированием
  `%`/`_` (`AbstractJdbcRepository.likePattern`); по дате — диапазон `start_time >= ? AND < ?`.
* Фильтрация (меню 5): по статусу, типу места, периоду, клиенту — параметризованные `WHERE`;
  по диапазону стоимости — Stream API в `BookingService.filterByPriceRange`.
* Сортировка (меню 6): `BookingService.sorted(field, ascending)` — `stream().sorted(field.comparator(asc))`,
  компараторы в enum `BookingSortField` (время начала, стоимость, статус, ник, длительность).
