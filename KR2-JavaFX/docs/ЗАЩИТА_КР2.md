# Защита КР2 — CyberClub (JavaFX)

Шпаргалка для всей команды: преподаватель может спросить любого участника о любой части.

## 1. Сценарий демонстрации (≈ 7 минут)

1. **Docker**: показать запущенные контейнеры примера из архива (раздел 4), открыть http://localhost:8080/ и `/actuator/health`.
2. **Запуск**: `run.cmd` → открывается главное окно, внизу строка «PostgreSQL: jdbc:postgresql://localhost:5432/cyberclub».
3. **Просмотр**: вкладка «Бронирования» — таблица; щелчок по строке → справа карточка: бронь + клиент + место (связанные данные).
4. **Добавление**: «＋ Новое бронирование» → клиент и место выбираются из списков, стоимость считается сразу → «Сохранить» → запись выделена в таблице.
5. **Валидация** в той же форме:
   - длительность `15` → поле красное, «допустимо от 0.5 до 12»;
   - время `25:99` → «время указано неверно»;
   - клиент Kirya2010 (15 лет) + место VIP → «Зона VIP доступна только клиентам 18+»;
   - занятое место/время → «Место … уже занято: бронирование #…».
6. **Редактирование**: двойной щелчок по строке со статусом «Создано» → форма с текущими значениями → изменить время.
7. **Смена статуса**: «Сменить статус» предлагает только допустимые переходы (Создано → Подтверждено/Отменено).
8. **Удаление**: «Удалить» → подтверждение «Да/Нет». Попробовать удалить «Активно» → понятный отказ.
9. **Поиск / фильтры / сортировка**: ввести `shadow`, затем `shadow vip`, `#12`; статус «Создано»; зона «VIP»; период; клик по заголовку «Стоимость»; список «Сортировка» + «по убыванию»; «Сбросить фильтры».
10. **Статистика**: «Статистика →» — 9 показателей по базе, 7 по текущей выборке, 2 диаграммы. Поставить фильтр на брони и вернуться — блок «Текущая выборка» пересчитан.
11. **Экспорт**: «Экспорт…» → выбрать папку и тип файла (.xlsx / .csv) → открыть файл в Excel.
12. **Клиенты / места**: CRUD клиента (ошибка: неверный телефон, повтор ника), брони клиента внизу; место — «На обслуживание».

## 2. Ответы на вопросы

**Как запускается JavaFX-приложение?**
`mvnw.cmd javafx:run` (плагин `javafx-maven-plugin` запускает `ru.mirea.cyberclub.CyberClubApp`) или класс `Launcher` из IDE.
JavaFX вызывает `CyberClubApp.start(Stage)`: читаем `database.properties`, проверяем подключение к БД
(`DatabaseManager.checkConnection`), создаём `AppContext`, загружаем `main-view.fxml`, создаём `Scene`, показываем `Stage`.
`Launcher` нужен потому, что класс-наследник `Application` нельзя запустить как обычный `main` без JavaFX на module path.

**Stage, Scene, Node?**
`Stage` — окно (главное окно; каждый диалог — тоже отдельный Stage). `Scene` — содержимое окна, корень графа сцены
и место подключения CSS. `Node` — любой элемент графа: `Button`, `TableView`, `BorderPane`, `Label`…
Контейнеры (`BorderPane`, `VBox`, `HBox`, `GridPane`, `FlowPane`, `SplitPane`) — тоже узлы, они раскладывают дочерние узлы.

**Зачем FXML?**
Разметка интерфейса отделена от логики: что и где лежит — в `*.fxml`, как реагировать — в контроллере.
Разметку легче читать, менять и открывать в Scene Builder; Java-код не превращается в сотни строк `new Button(...)`.

**Как FXML связан с Controller?**
- `fx:controller="ru.mirea.cyberclub.ui.controller.BookingsController"` — какой класс создать;
- `fx:id="table"` ↔ поле `@FXML private TableView<Booking> table;` — FXMLLoader внедряет объект в поле;
- `onAction="#onDelete"` ↔ метод `@FXML private void onDelete()` — обработчик события;
- `@FXML private void initialize()` вызывается после внедрения всех полей — там настраиваем таблицы и слушатели.
- Контроллеры создаёт `AppContext.createController` (передаётся в `FXMLLoader.setControllerFactory`),
  поэтому у контроллера есть конструктор `(AppContext)` и доступ к сервисам.
- Вкладки подключены через `<fx:include fx:id="bookings" source="bookings-tab.fxml"/>`;
  вложенный контроллер попадает в поле `bookingsController` главного контроллера (имя = fx:id + "Controller").

**Зачем ObservableList? Как обновляется TableView?**
`ObservableList` сообщает подписчикам о каждом изменении (добавили, удалили, заменили всё). `TableView` подписана
на свой список и перерисовывает строки сама — вызывать «обновить таблицу» вручную не нужно.
Цепочка в `BookingsController`:
```
master (ObservableList, данные из БД) → FilteredList (предикат поиска/фильтров) → SortedList (компаратор таблицы) → TableView
```
После добавления/изменения — перечитываем список из БД (`master.setAll(...)`) и выделяем запись; после удаления —
`master.remove(...)`. Загрузка из БД идёт в фоновом потоке (`FxTasks`, `javafx.concurrent.Task`),
а результат применяется в JavaFX Application Thread — менять интерфейс можно только из него.

**Как работает сортировка?**
`sorted.comparatorProperty().bind(table.comparatorProperty())`. Клик по заголовку меняет `sortOrder` таблицы →
таблица строит компаратор → `SortedList` пересортировывает данные. Ячейки хранят «сырые» значения
(`LocalDateTime`, `BigDecimal`, `Duration`), поэтому даты сравниваются как даты, а суммы как числа; формат «03.10.2026 19:00»
и «900.00 руб.» — только при отрисовке (`ui/util/Cells`). Список «Сортировка» программно ставит нужный столбец в `sortOrder`.

**Как реализованы поиск и фильтрация?**
Контроллер собирает значения элементов в `BookingFilter` (слой сервисов) и ставит `filtered.setPredicate(filter.toPredicate())`
при каждом изменении любого поля. Поиск: каждое слово запроса должно встретиться в номере, нике, ФИО, месте или комментарии
(`shadow vip`), `#12` — поиск по номеру. Фильтры: статус, зона, клиент, период. Если «по» раньше «с» —
`ValidationException`, поля периода подсвечиваются. Правила покрыты тестами `BookingFilterTest`.

**Где бизнес-логика?** В `service/` (перенесено из КР1): `BookingService` — правила бронирования (клиент и место существуют, место работает,
длительность 30 мин – 12 ч, не в прошлом, без пересечений, переходы статусов, 18+ для VIP/буткемпа и ночи,
расчёт стоимости), `ClientService` — форматы, уникальность ника/телефона/email, возраст ≥ 12, запрет удаления клиента с бронями,
`StationService`. Контроллеры только вызывают сервисы.

**Где работа с данными?** В DAO `repository/jdbc/*`: весь SQL там, только `PreparedStatement` с параметрами,
ресурсы закрываются try-with-resources (`AbstractJdbcRepository`). Подключение — `db/DatabaseManager`,
параметры — `database.properties` + переменные окружения (пароля в коде нет). Ограничения БД (`UNIQUE`, `CHECK`,
`FOREIGN KEY`, `EXCLUDE` против пересечений броней) — последняя линия защиты.

**Как обрабатываются исключения?**
- `SQLException` переводится в исключения приложения в `SqlErrorTranslator` (по SQLSTATE и имени ограничения → понятный текст);
- сервисы бросают `ValidationException` (с ключом поля) и `BusinessRuleException`;
- форма (`FormController.trySubmit`) ловит их: текст — под формой, неверное поле подсвечивается, окно не закрывается;
- действия в таблицах ловят ошибки и показывают `Dialogs.error` — только понятный текст;
- непредвиденные ошибки пишутся в журнал (SLF4J), пользователь видит «Непредвиденная ошибка…»; пустых `catch` нет.

**Как проверяются данные?** Два уровня: `FormInput` — заполненность, число/дата/время разбираются, диапазон, длина;
сервисы — смысл (формат телефона и ника, уникальность, дата рождения не в будущем, возраст, бронь не в прошлом,
пересечения, допустимый статус). БД — `CHECK`/`UNIQUE`/`EXCLUDE` на случай обхода.

**Как считается статистика?** «Показатели клуба» — агрегатные SQL-запросы в `JdbcStatisticsRepository`
(`COUNT`, `SUM`, `AVG`, `GROUP BY … ORDER BY cnt DESC LIMIT 1`). «Текущая выборка» — `StatisticsService.forBookings`:
Stream API по строкам таблицы (сумма/среднее/мин/макс без отменённых, средняя длительность, доля отменённых).
Диаграммы: `PieChart` по статусам и `BarChart` сумм по зонам.

**Как выполняется экспорт?** `BookingsController.onExport`: берём строки таблицы в текущем порядке → `FileChooser`
(путь и формат выбирает пользователь, есть фильтры *.xlsx и *.csv) → `ExportService` выбирает реализацию интерфейса
`Exporter` по расширению: `ExcelExporter` (Apache POI: лист «Бронирования» с настоящими датами и числами + лист «Показатели»)
или `CsvExporter` (UTF-8 с BOM, разделитель «;», экранирование по RFC 4180). Запись идёт в фоне, по окончании — сообщение с путём.

**CSS?** `ui/css/app.css` подключается к Scene и к каждому диалогу. Оформлены кнопки (`primary-button`, `danger-button`),
таблицы (полосы, выделение, отменённые брони серым), формы, заголовки, плашки статусов (`status-active` и т.д.),
ошибки (`field-error`, `error-label`). Цвета вынесены в переменные на `.root`.

## 4. Docker: пример из архива

1. Установить и запустить Docker Desktop (статус Running).
2. Из корня распакованного архива (`student-hub-suite-rebuilt`, там лежит `.env`):
   ```bash
   docker compose --env-file .env -f backend/docker-compose.yml up -d --wait
   ```
   Скрипт `backend/start-compose.ps1` из архива не сработает: он ищет в `docker-compose.yml` метку
   `STUDENT_HUB_COMPOSE_V3`, а её там нет.
3. Проверка: `docker compose --env-file .env -f backend/docker-compose.yml ps` (db — healthy, backend — running),
   http://localhost:8080/ и http://localhost:8080/actuator/health → `{"status":"UP"}`. Первый старт backend долгий:
   Maven внутри контейнера скачивает зависимости.
4. Вход: `admin@example.org` / пароль из `.env` (`BOOTSTRAP_ADMIN_PASSWORD`).
5. Их JavaFX-клиент: открыть `javafx-client` в IntelliJ IDEA и запустить `javafx:run` из окна Maven
   (или `mvn javafx:run`, если Maven 3.9+ установлен отдельно).
6. Остановка без удаления данных: `docker compose --env-file .env -f backend/docker-compose.yml down` (без `-v`).

Отличие нашей КР2 от примера: пример ходит в REST API (JavaFX → HTTP → Spring Boot → PostgreSQL),
а наше приложение подключается к своей базе КР1 напрямую через JDBC (JavaFX → Service → DAO → PostgreSQL).
